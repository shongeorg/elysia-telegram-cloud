# Cloud Player --- Android Media Session інтеграція

## Завдання для агента

Доопрацюй існуючий Vue 3 вебплеєр **Cloud Player --- Telegram Storage**,
щоб Android показував повноцінну картку відтворення у шторці сповіщень і
на екрані блокування.

Зараз аудіо відтворюється через `new Audio()`. Android показує назву
треку, назву Cloud Player, прогрес і кнопку паузи, але не показує повний
набір керування (попередній/наступний трек та інші доступні дії).

## Основна вимога

Інтегрувати **Web Media Session API (`navigator.mediaSession`)** з
поточною логікою плеєра.

**Не переписувати плеєр з нуля. Не замінювати Vue 3. Не змінювати
бекенд/API, структуру треків, дизайн сторінки або існуючу логіку черги
без необхідності.**

Перед змінами: 1. Прочитай весь поточний код проєкту. 2. Знайди реальні
функції запуску/паузи/перемикання треків, поточний `Audio`-об'єкт,
завантаження треків і структуру об'єкта треку. 3. Визнач, які поля
реально містять назву, виконавця, URL аудіо та обкладинку. Не вигадуй
поля. 4. Інтегруй Media Session у вже наявні функції.

## 1. Метадані поточного треку

Після успішного вибору треку та перед/під час запуску синхронізуй:

-   `navigator.mediaSession.metadata`
-   `title` --- назва треку з реального поля даних;
-   `artist` --- виконавець, якщо він доступний;
-   `album` --- альбом/джерело, якщо є;
-   `artwork` --- обкладинка, якщо доступна.

Якщо у треку немає виконавця або обкладинки, використовуй безпечний
fallback. Не формуй URL обкладинки з неперевірених даних. Якщо є тільки
назва файлу, не видавай її за окремо відомого виконавця.

Створюй `MediaMetadata` лише якщо API доступний:

``` js
if ('mediaSession' in navigator && 'MediaMetadata' in window) {
  navigator.mediaSession.metadata = new MediaMetadata({
    title: trackTitle,
    artist: artist || 'Cloud Player',
    album: album || 'Telegram Storage',
    artwork
  });
}
```

Це лише орієнтир: використовуй реальні змінні та поля проєкту. Не
вставляй приклад буквально, якщо він не відповідає фактичному коду.

## 2. Кнопки керування Android

Зареєструй `navigator.mediaSession.setActionHandler()` для доступних
дій:

-   `play` --- запустити/відновити відтворення;
-   `pause` --- поставити на паузу;
-   `previoustrack` --- перейти до попереднього треку через існуючу
    функцію;
-   `nexttrack` --- перейти до наступного треку через існуючу функцію;
-   `seekto` --- переміститися до заданої позиції, якщо браузер
    підтримує цю дію;
-   `seekbackward` та `seekforward` --- за потреби реалізувати
    перемотування через наявну логіку.

Використовуй наявні функції плеєра. Не дублюй окрему логіку `next`,
`prev`, `toggle` у Media Session handlers.

### Важливо

-   Обробник `play` має запускати відтворення, а не перемикати його на
    паузу, якщо поточний стан уже playing.
-   Обробник `pause` має гарантовано ставити на паузу.
-   `previoustrack` і `nexttrack` мають використовувати фактичну
    чергу/поточний індекс плеєра.
-   Враховуй повтор, shuffle та фільтрацію, якщо вони вже реалізовані.
-   Не допускай запуску треку, у якого немає валідного аудіо URL.
-   Якщо дія не підтримується браузером, обробляй це без падіння
    застосунку.

## 3. Синхронізація стану

Синхронізуй `navigator.mediaSession.playbackState` з реальним станом
`Audio`:

-   `playing` після фактичного початку відтворення;
-   `paused` після паузи, завершення або зупинки;
-   не встановлюй `playing` лише після натискання кнопки, якщо аудіо не
    почало відтворюватися.

Використовуй події реального `Audio`-об'єкта, наприклад: - `play`; -
`playing`; - `pause`; - `ended`; - `loadedmetadata`; -
`durationchange`; - `timeupdate`.

Не створюй зайві дублікати listeners. Якщо вони додаються під час mount,
забезпеч cleanup під час unmount.

## 4. Прогрес і позиція

Підтримай позицію відтворення через
`navigator.mediaSession.setPositionState()` за можливості.

Перед передаванням позиції перевір: - `duration` --- скінченне число та
більше нуля; - `position` --- скінченне число та не від'ємне; -
`position` не перевищує `duration`; - `playbackRate` --- валідне число.

Не викликай `setPositionState()` з `NaN`, `Infinity`, невідомою
тривалістю або некоректними значеннями.

Оновлюй позицію в потрібних аудіоподіях, але не створюй безконтрольний
таймер або надмірні оновлення. Якщо API недоступний --- вебплеєр повинен
продовжувати працювати як раніше.

Обробник `seekto` повинен: 1. перевірити `seekTime`; 2. обмежити його
допустимим діапазоном треку; 3. оновити `audio.currentTime`; 4.
синхронізувати Vue-стан прогресу.

## 5. Android / Chrome поведінка

Перевір сценарій у мобільному браузері Android:

1.  Відкрити Cloud Player.
2.  Запустити трек.
3.  Згорнути браузер або відкрити шторку сповіщень.
4.  Перевірити назву треку, виконавця/джерело, обкладинку, паузу та
    перемикання.
5.  Заблокувати екран і перевірити доступні елементи керування.
6.  Натиснути pause/play з системної картки.
7.  Перевірити next/previous, якщо браузер їх показує.
8.  Перевірити, що керування не зупиняє аудіо та не запускає інший трек
    помилково.

Не гарантуй, що Android покаже абсолютно всі кнопки: набір контролів
залежить від браузера, версії Android, доступних Media Session actions і
системного UI. Але вебзастосунок має правильно декларувати підтримувані
дії.

## 6. Життєвий цикл і сумісність

-   Перевір наявність `navigator.mediaSession` та відповідних методів.
-   Не допускай помилки, якщо API відсутній.
-   Не змінюй роботу плеєра на desktop або браузерах без Media Session.
-   Не додавай сторонні бібліотеки, якщо нативного API достатньо.
-   Не використовуй `setInterval` для постійного опитування, якщо можна
    використати події `Audio`.
-   Якщо додаєш глобальні listeners, прибирай їх при завершенні
    життєвого циклу компонента.
-   Якщо action handler неможливо зареєструвати, обробляй виняток окремо
    для конкретної дії.
-   Не зупиняй аудіо через `visibilitychange`, `blur` або приховування
    вкладки.

## 7. Не ламати існуючу функціональність

Залиш працездатними: - список треків; - пошук; - вибір треку; -
play/pause; - next/previous; - shuffle; - repeat; - перемотування; -
регулювання гучності; - поточний трек та його підсвічування; -
завантаження списку з існуючого `/api/music`.

Не змінюй дизайн та HTML-контролі, якщо для Media Session це не
потрібно.

## 8. Перевірки після реалізації

Перевір: - запуск треку з рядка списку; - запуск і паузу з кнопки
сторінки; - запуск і паузу з Android media notification; - перехід
next/previous з Android; - коректну назву поточного треку після
перемикання; - синхронізацію системного прогресу; - трек без
обкладинки; - трек без окремого поля виконавця; - трек без валідного
URL; - порожній список; - повторне перемикання треків; - відсутність
Media Session API; - відсутність помилок у Console.

## 9. Формат завершення роботи

Після змін надай короткий звіт:

1.  Які файли змінено.
2.  Які Media Session actions реалізовані.
3.  Як синхронізуються metadata, playback state та позиція.
4.  Що перевірено.
5.  Що не вдалося перевірити фізично на Android.
6.  Які обмеження залежать від Chrome/Android.

Не заявляй, що Android-картка повністю протестована, якщо реального
тесту на пристрої не було.

## Критерій готовності

Після запуску аудіо Android має отримувати актуальні метадані треку та
підтримувані команди керування через Media Session. Кнопки системної
картки повинні викликати ті самі функції плеєра, що й інтерфейс сайту.
Відсутність Media Session API не повинна ламати звичайне відтворення.
